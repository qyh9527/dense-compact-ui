# 与 Impeccable 配合

本技能可独立使用。Impeccable 是可选的审计与改进工具；本文件不安装它，不注册命令，也不要求为一次局部修改补齐它的运行环境。

## 分工与优先级

- 用户当前要求、项目已确认的设计约定优先。已选择紧凑风格时，由本技能维护空间预算、密度、连续分区与圆角角色；Impeccable 补充审计、任务评审、文案和边界检查。
- 选择「只借用检查」时，沿用现有品牌和设计系统；仅同时加载两个技能不代表同意换主题或改密度。
- 遇到相互冲突的建议，写明它解决的实际问题与适用设备，再按已确认约定取舍。品牌或密度偏好不能成为放弃键盘、对比度、缩放和有效热区的理由。

## 可借用的工作方式

| Impeccable 能力 | 在紧凑界面中的用途 | 约束 |
| --- | --- | --- |
| audit / critique | 分别检查实现缺陷、任务与层级问题 | 使用 quality-workflow.md 的证据格式；审计或评审本身不授权改文件 |
| polish | 对齐、状态、token 与组件一致性 | 保留既有视觉语言和业务行为 |
| distill | 清理包装、重复说明、装饰噪声 | 保留比较列、批量操作和全量总览需求 |
| clarify / harden | 操作文案、失败恢复、长内容与本地化 | 沿用产品术语，只覆盖支持的平台与语言 |
| adapt / optimize | 窄屏重组与性能诊断 | 断点不自动换密度；分页按任务、渲染策略按实测成本决定 |
| extract / document | 归纳复用 token、组件和项目设计约定 | 先查现有实现，避免创建平行的设计系统 |

这些名称是能力映射，不是本仓库提供的新命令。要实际运行 Impeccable，先核对已安装版本的入口与帮助；未安装或工具不可用时，直接用本技能的参考文件完成可做的检查，并标出验证限制。

## 遇到通用建议时怎么取舍

| 通用建议或告警 | 在当前项目中核对什么 |
| --- | --- |
| 增加留白、放大正文、减少每屏信息 | 先测可读性与任务需求；密度按用户选择，只给分组增加必要间隔，聚焦型任务沿用标准尺寸 |
| 控件太小 | 分开测视觉尺寸和真实命中区域；触屏按现有热区规则处理，热区必须参与布局且互不重叠 |
| 减少边框、删除侧栏、改成单列 | 判断是否破坏连续分区、比较关系和常驻上下文；保留承担分组或导航功能的结构 |
| 换字体、加亮色或动效来增强特色 | 先用任务层级、对齐与状态解决问题；主题、字体和动效沿用项目约定 |
| 补齐深浅主题 | 按用户需要与项目已有主题范围验证；新建默认主题仍按 color.md，不为检查项凭空加主题 |
| 字体 / 卡片 / 间距的反模式检测命中 | 命中只是线索；核对产品场景、源码及实际渲染，再决定修复或记录有理由的局部例外 |

## 检测与证据

1. 若已有检测报告，先核对目标文件、版本和范围，避免拿旧结果指导新界面。需要重跑时使用当前安装提供的命令；已有自动检测结果可复用，不重复跑同一轮。
2. 对每条相关告警记录「确认缺陷 / 有意设计 / 待验证」及依据。仅因采用紧凑风格不能批量忽略告警；例外只覆盖具体规则与位置，不关闭整类可达性检查。
3. 区分源码检测、浏览器量取、键盘操作、合成触屏与真机验证。窄屏截图证明布局表现，不证明软键盘或触屏手势可用；零告警也不能代替真实任务复验。

## 复用项目上下文

已有 PRODUCT.md 时读取受众、主要任务和使用环境；DESIGN.md 与页面覆盖文件负责已落地的视觉约定。按来源区分用户确认的事实与从代码观察到的现状，不能从配色推断品牌或用户身份。

沿用项目已有文档位置，不为了兼容重复创建产品说明。局部打磨不因缺 PRODUCT.md 而阻塞；只在缺失信息会改变任务或设计方向时问一个具体问题。整理 DESIGN.md 时使用 design-md.md，更新相关条目而非整份覆盖。

## 使用示例

「用 dense-compact-ui 评审这个工作台，保留现有主题与密度；按问题影响排序，只报告。」

「修复刚才确认的 P1 / P2 问题；保留比较列和常用操作，按相同数据与视口复验。已安装 Impeccable 时可复用其审计结果。」
