# 审计、评审与定向改进

根据请求选一条路径，只读该路径需要的专题。先完成 SKILL.md 的风格选择；「只借用检查」时以项目现有设计系统为准，不套用本技能的主题或密度默认值。

## 选路径

| 请求 | 做什么 | 完成条件 |
| --- | --- | --- |
| 审计、audit、查问题 | 对照 verify.md 检查可达性、状态、布局、主题与性能；只报告，不改文件 | 每项发现有位置、证据、影响和复验方法；未覆盖项注明 |
| 设计评审、critique、为什么不好用 | 沿主要任务检查信息层级、查找与比较、操作距离、上下文保持；只报告，不改文件 | 区分可证实的缺陷与设计建议，说明对当前任务的影响 |
| 打磨、polish、统一细节 | 修正范围内的对齐、token 漂移、状态与文案不一致 | 主要任务复验通过，既定品牌、信息架构和行为保持一致 |
| 精简、distill、去模板味 | 删重复包装与信息，合并重复说明；按操作频率安排入口 | 必需字段、批量比较和常用操作仍可达，空间收益有对照 |
| 加固、harden、边界情况 | 按目标设备补长内容、空值、失败恢复、权限与网络异常 | 失败后输入、选择和恢复入口可用；未验证的状态明确列出 |

「评审并修复」授权先报告发现再实施，不必再次询问；仅要求评审时停在报告。局部请求只处理指定区域，只有共享组件确为根因时才扩大修改，并检查受影响的使用处。

## 选验收档位

路径决定做什么，验收档位决定验到多深。三档共用同一套规则、优先级和报告格式。

| 档位 | 何时用 | 做什么 | 结论上限 |
| --- | --- | --- | --- |
| 轻度 light | 单个非共享组件的局部改动：对齐、间距、圆角、颜色微调，编辑中的持续反馈 | 改动处、1–2 个视口、改动相关的状态；Web 跑一次 audit-script.md 的命令行（可一次传两个 `--viewport`），截图只在需要时取改动处 | partial：写「轻度检查范围内未发现」，不写验收通过 |
| 中度 standard | 一个功能或页面区域、共享组件，或新增 / 改变了状态（展开、错误、空、加载） | 先写一行范围：受影响页面 × 2–3 个视口 × 相关状态；Web 用 `--steps` 操作到各状态再量，按需加 `--scroll`、`--color-scheme`；共享组件查有代表性的几处使用；过一遍 verify.md 里与范围相关的项，修后同条件复验 | 范围内都查完是 verified，否则 partial；只对写下的范围成立 |
| 全套 full | 新页面、改版、全局 token / 全局样式 / 布局系统、导航 / 登录 / 重要表单等关键流程、跨平台目标、发布前、用户要求完整验收 | 先写验收契约，按风险取样，量取 + 主路径与异常路径操作 + 观感检查，修后同条件复验 | verified / partial / blocked |
| 自动 auto | 用户没指定时的默认 | 按下面的顺序选，报告写明选了哪档和理由 | 同所选档位 |

自动选择按顺序判断：

1. 用户指定的档位优先。要求全套验收不等于授权改代码、装依赖、重启服务或部署。
2. 全局 token、全局样式、布局系统、导航、登录或重要表单，新页面、改版、发布前 → 全套。按影响半径判，不按改动行数：一行全局 token 也走全套。
3. 一个功能或页面区域、共享组件，或新增 / 改变了状态 → 中度。
4. 影响限于一个非共享组件、也不改状态 → 轻度。
5. 判不清影响范围 → 往高一档取；只能做低一档时结论标 partial 并写升级建议。

逐档升级。轻度升到中度：检出 P0 / P1；改动其实还影响别的使用处或状态；量到横向溢出、点击被拦截、字体回退但定位不到根因。中度升到全套：检出 P0；同一问题出现在多个页面，或根因在全局样式 / token；同一问题在不同视口或主题下表现矛盾；用户要的是交付验收。先排除合法例外（表格内横向滚动、对话框有意遮挡）再升级。用户限定档位时不自行升级，在报告里写升级建议和未覆盖项。

## 验收契约

全套动手前写下；中度只写上表那一行范围；轻度只写目标。

- **目标**：页面 / 路由 / 窗口与版本。报告里的 URL 去掉凭据和含令牌的查询参数。
- **任务与状态**：主要任务；只列与任务相关的状态（默认、加载、空、错误、展开、选中、焦点、长内容、低权限）。
- **视口与输入**：按判读的形态与输入取。Web 常用 1280×720、390×844、360×740、矮视口与 200% 文字缩放；桌面、原生按 context.md 的验证适配器。
- **预算**：页面、视口、状态与修复轮次的上限。按「任务 × 状态 × 视口 × 输入」的风险取样，不跑全组合。
- **授权**：只审计（默认）/ 可改代码 / 可重启预览 / 可部署，各自单独授权，不互相推导。删除、发送、支付、改真实数据这类操作只在模拟数据或沙箱里测；用 audit-script.md 的 `--steps` 自动操作时同样遵守。
- **证据能力**：本次能拿到哪几级证据（见下表），拿不到的写进未覆盖。

## 证据等级与结论

| 级 | 来源 | 能支持 | 不能支持 |
| --- | --- | --- | --- |
| A | 目标窗口或真实浏览器里走完的操作路径 | 用户实际看到、操作到的结果 | 没走过的设备与状态 |
| B | 同一状态下的 DevTools / CDP 量取、E2E、WebView 或框架 UI 测试 | 几何、样式、状态可达、特定交互 | 原生壳、系统弹窗等没测的部分 |
| C | 无头量取（如 audit-script.md 的命令行） | 指定视口下的溢出、遮挡、字体、密度线索 | 整体观感与可用性 |
| D | 源码、静态规则、构建与单元测试 | 风险提示 | 渲染已经合格 |

等级是证据类型，不是质量排序：几何问题上，确定性的 B / C 级量取往往比看一眼截图可靠。

结论只用三种：**verified**（契约或中度写下的范围内，状态、视口和证据要求都检查过，没有未解决的 P0 / P1）、**partial**（只覆盖一部分，不能推广；轻度最高到这里）、**blocked**（目标不可达、环境或授权缺失，无法下结论）。退出码 0、零告警、截图看着不错都不等于 verified。修复后另写复验状态：同条件已复验 / 部分复验 / 无法复验。

报告第一行写：`验收档位 <light / standard / full>（理由）｜结论 <verified / partial / blocked>｜已覆盖 <视口、状态>｜未覆盖 <…>｜授权 <只审计 / 可改代码>`。

## 建立基线

1. **限定目标。** 记录页面 / 组件、主要任务、平台与形态、当前状态、可改范围及已有设计约定。优先用当前请求、DESIGN.md、已有 PRODUCT.md 和项目文档；区分已确认事实与推断。缺少文档本身不阻塞局部改进。
2. **选代表性内容。** 使用同一组字段、记录、筛选和选中状态做前后比较。涉及已有项目时先读 redesign.md；密度数值与测量口径沿用 layout-density.md、verify.md，不另建评分尺。
3. **检查真实路径。** 从进入页面到完成主要操作，覆盖任务相关的加载、空、成功和失败状态。桌面工作台重点走比较 / 批量操作与键盘路径；手机任务重点走触屏、软键盘与返回恢复。未执行的路径不能写成测试通过。

## 写可执行的发现

每条发现使用：`优先级｜位置｜证据（等级）与验证方式｜用户影响｜最小改法｜复验方法`。同一根因合并，列出受影响区域。视觉问题按它对查找、辨认和操作的影响定级；与任务无关的纯偏好单列为建议。

| 优先级 | 判断依据 |
| --- | --- |
| P0 阻断 | 核心任务无法完成、工作内容丢失或结果状态误导 |
| P1 严重 | 主要操作明显受阻、关键内容不可读或可达性要求不满足 |
| P2 一般 | 存在绕行方式，但增加查找、操作或理解成本；包括层级糊成一片、主操作或当前状态难以辨认、签名元素被破坏 |
| P3 打磨 | 不影响完成任务的局部一致性问题 |

先按真实影响定优先级，同级再按 SKILL.md 的领域顺序排。没有运行性能测量时只报告可核对的风险；没有截图或运行界面时只做静态结论。不把检测告警数量或主观总分当成可用性证明，也不凭有限检查宣称全面符合无障碍标准。

## 定向修改

- **打磨：找最小责任层。** 局部偏差改局部；重复偏差查共享组件；已有 token 能表达时直接复用，只有实际复用需求才新增 token。缺少 DESIGN.md 时先沿用一致的现有实现，不把项目判成空白画布。
- **精简：先减噪声，保留签名元素。** 签名元素是这套空间语言本身：1px 分隔线分区、按角色分层的圆角、`tabular-nums` 数字、强调色配额与中性主按钮；精简只去重复包装，签名元素原样保留。先去掉重复边框、容器和说明，再考虑折叠低频内容。为每个移走的字段或操作说明去向；表格的比较列、状态和高频操作优先常驻。不得为减少元素数量破坏一屏总览或把所有行内操作藏进菜单。
- **加固：按失败路径补齐。** 只检查产品支持的设备与语言；关注加载后无数据、超时重试、权限不足、重复提交和部分失败。让用户知道哪些成功、哪些失败，保留尚未完成的输入与选择。触屏热区与控件视觉尺寸分别检查。
- **文案：说清动作和恢复。** 按钮写出动作与对象，错误提示给出可执行的下一步；沿用产品术语。保留事实性声明、法律文案和业务含义，既有受保护约定按 redesign.md 处理。

## 复验与停止

1. 改前记录基线，集中修复本次范围内的发现；按 verify.md 用同一内容、视口、主题和状态复验，说明任务相关的检查覆盖。
2. 有预览条件时，首次检查一次采集适用的窗口 / 设备、长内容、文字缩放和任务状态，按影响批量修正；第二次只确认修改处和共享组件受影响处。
3. **观感检查。** 确定性缺陷收敛后再做，避免为观感反复改共享 token。停止前把同一内容的前后截图并排看一次整体：对齐线与间距节奏是否一致，组件越密分组间距是否越开；标题、正文、次要信息的层级对比是否拉开；强调色是否守住 color.md 的配额；签名元素是否完整。观感判断写明依据（主要任务、DESIGN.md 或项目现有约定），标为设计建议，不打总分、不当通过门槛；「只借用检查」时以项目自己的设计系统为准。影响辨认或操作的观感问题按优先级修，纯偏好列为建议。观感通过后停止样式微调；有明确未解决缺陷时继续针对该缺陷处理，不以轮数代替完成条件。
4. 交付时逐项标「已修复 / 未解决 / 建议」及「预览验证 / 静态检查 / 未验证」。在目标运行环境检查时附截图或量取记录，平台与单位按 context.md；静态改动不能证明触屏、焦点或视觉效果已通过。

只有已授权范围完成、关键发现已复验或如实列明限制，才结束本轮。遇到新方向建议单独列出，不自动扩成整页重做。
