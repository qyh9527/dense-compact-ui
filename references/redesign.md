# 改版与已有项目

## 先判模式

| 模式 | 什么时候 | 做法 |
| --- | --- | --- |
| 新建 | 没有现成界面，或用户同意推倒重来 | 用本技能默认值 |
| 改版·保留 | 要现代化，但不换品牌 | 先审计，抽出现有 token，逐步演进 |
| 改版·重做 | 新视觉语言套在原有内容上 | 视觉按新建处理，内容和信息架构保留 |

判不清时问一次：「这次改版保留现有品牌，还是视觉上从头来？」

## 先审计，再动手

先记下现状，再提方案：

- **技术栈与组件库**：从 `package.json`、`pubspec.yaml`、`*.csproj` 等项目文件识别，不假定。引入新依赖前先查是否已安装，缺的给出安装命令。
- **现有 token**：颜色、字体、圆角、间距、密度，按空间 / 交互 / 主题三层归类。
- **信息架构**：页面树、主导航、关键路径。
- **要保留的**：用户熟悉的布局位置、标志性交互、已有的可达性成果（焦点样式、标签、键盘路径）。
- **要淘汰的**：嵌套卡片、装饰性状态点、到处都是的品牌色、窄屏下坏掉的布局。

## 不悄悄改的东西

下列改动先取得用户明确同意：

- 路由、URL、锚点 ID
- 主导航的文案和顺序
- 表单字段的 `name` 和顺序（影响自动填充和数据对接）
- 埋点依赖的按钮文案、元素 ID、类名
- Logo、品牌字标、法律与隐私文案

## 已有设计系统

项目已经用 Fluent、Carbon、Primer、Material、Ant Design、Element Plus 等组件库时：

- 沿用官方包和它的主题机制，不手写 CSS 仿一个；也不导入整套 token 后覆盖掉九成。
- 本技能只提供空间组织、密度建议和检查清单，密度通过组件库自带的尺寸选项实现（如 Carbon 组件的 `size`、Ant Design 的 `componentSize`）。
- 一个项目只用一套组件库。

## 演进顺序

从风险低、收益高的开始，满足需求就停：

1. 删冗余：重复包装、重复标签、无用空行
2. 间距与对齐：统一关系间距，行高配套
3. 字体与数字：固定字阶，`tabular-nums`
4. 色彩收敛：普通操作回到中性色，强调色回到配额内
5. 结构重组：承载结构、窄屏外壳
6. 整块替换：现有区块确实救不回来时才做
